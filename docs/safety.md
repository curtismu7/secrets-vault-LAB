# Safety

- Loopback bind only (`SVLAB_BIND` is the explicit opt-in the container uses); the compose file publishes `127.0.0.1` only (a test pins it). The container runs as a non-root user, read-only, with every capability dropped.
- Host header must be a loopback name; writes must be same-origin.
- Netguard blocks every outbound connection (fetch, socket, DNS, UDP) with a self-test, and a test asserts zero attempts in the server process across the whole API in both modes. There is no worker thread and no child process. The five secret managers, the three key providers, the gateway and the backends are in-process models; the "API calls" are descriptions on `.example` hosts. Nothing is sent.
- **No API ever returns a stored value.** A vault entry shows present, size in bytes, version, last changed, a mask and the first 8 hex characters of its (non-secret) nonce. A store read hands the value to a simulated consumer and the answer carries only names, sizes and a mask. The provider connection credentials are sealed at rest and never shown. A test types values into every endpoint and searches every answer, every state, the hop panes, the audit trail and the process output; another does a full flow of mock values and searches all answers; the no-copy proof searches everything the Privilege side keeps for every value the providers hold (plain, base64, hex), with a planted-copy self-test. Only lab-labelled `MOCK-` values are ever generated; even those are never displayed.
- **Strictly self-service.** The caller comes from `X-Lab-Actor` (a lab stand-in for the verified token), is checked against the roster, and its role is taken from the roster, never from the request. Every vault function takes the caller and no owner; there is no parameter, query, body field or role that names another vault (a test tries every role on every path; an `owner` is refused with 400, never ignored). Another person's entry id and an id that never existed give the same "not found". The administrator restarts the key service and edits the target list and grants: none of that reads a credential. Removing a target deletes the entries that pointed at it (counts only in the audit).
- **Encryption.** Real AES-256-GCM (`node:crypto`), a fresh random 12-byte nonce per value (the engine refuses to reuse one and draws again), the user id and entry id as additional authenticated data (a sealed value moved to another user's entry, or another entry, fails to open; tampering with the ciphertext, tag, nonce or AAD is detected and audited). The key comes from one of three in-process mock providers; the compiled-in development key is derived from a public string, protects nothing, and the page says so loudly.
- **Credential-shaped values the visitor types are masked or refused, and the lab says it is a heuristic.** Names, paths, tags and header names that look like a credential are refused (never echoed, never kept); notes and free text are cleaned (zero-width and bidi characters deleted, control characters turned into spaces, credential-shaped runs masked, then cut to length); every JSON answer is masked again by the specific detectors as defence in depth, which is why every fixed refusal message is tested to pass the mask unchanged. Error messages are fixed text and never include input; the first hop pane shows the route pattern, never the path, and a `secret`, `fields` or `value` body is replaced by a write-only marker; unknown keys are refused without naming them; the final 404 and error handlers answer fixed JSON for every method and path; a workspace id that looks like a credential is refused rather than echoed.
- **Refusals as data.** The page sends `refusalsAs200: true` with every write. It changes one thing: an engine refusal comes back as HTTP 200 with `ok: false` and the error code (a 401 never does), because a browser logs every 4xx as a console error and a refusal the visitor asked for is the point of the demo. The isolation check deliberately reads other people's entries and logs the 404 and 400 answers as console messages. The Host check, same-origin writes, `bad_mode`, `unknown_field`, a malformed body, the body size limit and every Mock write (409) stay real 4xx errors.
- Every value used as an object key (provider, target, shape, vertical, scenario, actor) is checked with `Object.hasOwn` or a find and a type test; an unknown vertical or scenario falls back, an unknown provider or target is refused.
- Input is bounded: bodies 200 KB, 500 entries and 64 KB (65536 bytes) per credential, 1 to 5 header pairs, 20 targets, 400 inventory secrets, 100 grants, 2000 audit entries, 40 hops per answer, one clock move at most 7 days, a store field at most 4096 bytes. A full workspace refuses new work whole with a clear code (Reset) instead of dropping anything; a new workspace beyond the 500-workspace cap is refused (503) instead of evicting another visitor. The backend and gateway logs keep the last 300 calls and say so. Writes in one workspace are serial (one engine, synchronous), and parallel requests are tested at the 500-entry cap.
- The server writes no file. The one home-directory touch is reading the optional shared settings file (`~/Development/.env`, or `STANDALONE_ENV`) with `util.parseEnv`, taking only `SVL_LAB_MODE`.
- Only `.example` and `.invalid` hosts appear in any shipped text (a doctor check scans the filled story in every vertical). The people, backends and store containers are synthetic.
- Every product claim is labelled "Ping release claim, UNVERIFIED on our tenant" in the banner of every tab, in presenter mode too. Each field is tagged as a deck claim, a lab reading or lab-invented.
